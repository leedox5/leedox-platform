# 15. Pull Request를 만들다

*(이 챕터는 시나리오가 아니라 실제로 겪은 이야기다 — 다상품 플랫폼 일반화 PR(#9)이 병합되며 완결됐다.)*

지금까지는 대부분 이런 흐름이었다. 요청하면 바로 main 브랜치에 커밋해서 push한다. 작은 팀, 빠른 반복에는 이 방식이 잘 맞았다. 그런데 Chatdox·Claudox를 각각 20장짜리 하나의 상품으로만 팔다가, "상품을 더 늘릴 수 있는 구조로 가자"는 결정을 내리면서 처음으로 그 방식이 안 맞는 작업이 생겼다.

## 왜 지금 PR인가

발단은 "20장이 좀 많게 느껴진다"는 생각이었다. 처음엔 기존 20장을 두 시즌으로 쪼개는 안(A안)을 떠올렸는데, 검토해보니 그건 진짜 문제를 안 풀고 있었다 — 지금 코드는 Chatdox와 Claudox가 완전히 별도로 구현돼 있어서, 상품을 쪼개든 늘리든 매번 코드를 새로 짜야 하는 구조였다. 그래서 방향을 바꿨다. 콘텐츠는 그대로 두고, **상품이 몇 개든 코드 변경 없이 등록 가능한 구조**부터 만들기로 했다(`chatdox/multi_product_platform_plan.md`). 6단계짜리 계획이 됐다.

이 작업은 예전 handoff들과 성격이 달랐다. 한 라운드로 끝나는 게 아니라 여러 단계(감사 → 설계 → 마이그레이션 → 정리 → 검증)에 걸쳐 코드가 계속 쌓이는 작업이었다. 그래서 "매 라운드 main에 바로 커밋" 대신, 처음으로 **브랜치 하나를 여러 라운드 동안 이어 쓰고, Pull Request로 진행 상황을 계속 보여주는** 방식을 쓰기로 했다.

## 브랜치를 열고, PR을 미리 연다

1단계(감사) 요청을 넣으면서 브랜치명을 `feature/generic-content-platform`으로 정했다 — 이후 단계도 전부 이 브랜치를 재사용하기로.

1단계가 끝나자 PR이 열렸다. [#9](https://github.com/leedox5/chatdox-platform/pull/9), 제목은 "다상품 콘텐츠 플랫폼 일반화 (1~4단계)". 그런데 GitHub 화면에 Merge 버튼이 안 보였다 — **Draft** 상태였기 때문이다.

이게 처음 겪는 개념이라 물어봤다. Draft는 브랜치 작업 중에 저절로 되는 상태가 아니라, PR을 만드는 시점에 명시적으로 선택해야 하는 옵션이었다(`gh pr create --draft`). "아직 다 안 끝났으니 지금은 리뷰하지 마세요"라는 신호를 일부러 켜둔 것 — 커밋 추가, 코멘트, CI는 평소 PR과 똑같이 다 되지만 Merge만 막혀 있었다. 여러 단계에 걸쳐 커밋이 쌓이는 작업이라, 막판에 큰 diff를 한 번에 보는 대신 진행 상황을 계속 보여주는 쪽을 택한 것이었다.

## 1단계: 감사에서 나온 것

첫 단계는 코드를 고치는 게 아니라 조사였다 — 지금 구조에서 "상품마다 새로 코드를 짜야 하는 지점"이 정확히 몇 개나 있는지부터 확인해야 2단계(설계) 범위를 잡을 수 있었다.

결과는 34개 지점, 그중 핵심만 13곳. 제일 눈에 띈 발견은 "상품별 챕터 목록 + 완료 상태 조회"라는 똑같은 문제가 **네 군데에서 서로 다르게 재구현**돼 있었다는 것이다 — `Curriculum`(Chatdox 모델), `Claudox`(Claudox 모델)뿐 아니라, 마케팅 페이지 컨트롤러가 `setup.md`를 또 다른 정규식으로 파싱하고 있었고, 어드민 진행률 화면도 `88_progress.md`를 완전히 별도로 파싱하고 있었다. 처음 예상은 "모델 2개를 합치면 된다"였는데, 실제로는 4개의 서로 다른 구현을 하나로 모아야 하는 일이었다.

덤으로 하나 더 나왔다 — 홈페이지 미리보기 화면(`_proof.html.erb`)의 Claudox 쪽이 모델을 아예 안 쓰고, 챕터 제목을 뷰에 직접 문자열로 박아둔 상태였다. 실제 콘텐츠가 바뀌어도 이 화면은 절대 안 바뀌는, 눈에 안 보이는 "가짜 동기화"였다. 이번 감사 범위는 아니었지만 따로 기록해뒀다.

## 지금 정해진 것들

작업이 몇 단계에 걸쳐 진행되다 보니, 진행 방식 자체도 몇 가지 정해야 했다.

- **Draft PR을 초기에 미리 연다**: 진행 상황이 계속 보이는 쪽이, 막판에 한 번에 리뷰하는 것보다 낫다고 판단해서 정식 관례로 확정했다.
- **최종 Merge는 구현하는 쪽이 직접 실행한다**: 지금까지 모든 작업에서 실제 git 조작(commit/push)을 구현하는 쪽이 직접 해온 것과 같은 원칙이다. 승인은 채팅으로 하고, GitHub 버튼을 직접 누를 필요는 없게 했다.

## 2~4단계: 설계, 마이그레이션, 정리

2단계(설계)에서 좋은 판단이 하나 있었다 — Chatdox를 곧바로 Claudox와 같은 파일시스템 스캔 방식으로 옮기려다가, 실제로 20개 챕터 제목을 하나하나 대조해보고서야 하드코딩된 제목과 실제 마크다운 헤딩이 전부 다르다는 걸 발견했다. 그래서 억지로 통일하지 않고, Chatdox만 과도기 어댑터를 씌워 남겨뒀다. 추측이 아니라 직접 대조해서 알게 된 사실이었다.

3단계(마이그레이션)에서는 실제로 옛 모델들을 지웠다. 그 과정에서 홈페이지 미리보기 화면의 오래된 하드코딩(1단계에서 발견했던 "가짜 동기화")을 고치다가, 원래 그 화면이 보여주던 챕터 4개가 순차적인 게 아니라 일부러 고른 비연속 선택이었다는 걸 알아채고 그 선택 자체는 그대로 지켰다 — 설계 문서가 제안한 단순한 방법을 그대로 따르지 않고, "동작을 완전히 똑같이 유지한다"는 원칙을 설계보다 더 엄격하게 지킨 순간이었다.

4단계에서는 남은 하드코딩들을 정리하다가 실제 버그를 두 개 더 발견했다 — 부록 챕터까지 섞여 "완성 22/20"으로 잘못 뜨던 것, 그리고 Claudox 랜딩 페이지만 가격 앵커를 못 받고 있던 오래된 비대칭. 둘 다 회귀 테스트와 git log 추적으로 원인까지 밝혀서 고쳤다.

## 5단계: 세 번째 상품으로 증명하다

계획은 원래 여기서 가벼운 가짜 상품 하나로 검증하고 끝내는 것이었다. 그런데 마침 새로 구상하던 무료 입문 상품("AI, 오늘부터 시작", 5화)이 있어서, 이걸로 검증과 실제 출시를 한 번에 하기로 했다.

결과는 `git diff`로 직접 확인했다 — 콘텐츠를 다루는 코드 파일은 단 한 줄도 안 바뀌었다. 바뀐 건 상품 데이터 등록과 동기화 스크립트의 한 줄뿐이었다. "새 상품 = 콘텐츠 폴더 + 상품 데이터 한 줄"이라는, 애초에 이 작업을 시작한 이유가 실제 콘텐츠로 증명된 순간이었다.

## 병합 직전, 안전장치에 한 번 더 걸리다

5단계까지 통과하고 나서, 마지막 병합을 진행하기로 했다. 계획대로라면 여기서부터는 간단했다 — Draft를 풀고, `gh pr merge`로 병합하면 끝. "실제 Merge 버튼 실행은 구현하는 쪽이 직접 한다"는 규칙도 이미 몇 단계 전에 정해뒀던 참이었다.

그런데 정작 병합을 실행하려는 순간, DEV 쪽에서 막혔다. Draft 해제까지는 됐는데, `gh pr merge` 자체가 "Blocked by classifier"로 거부된 것이다. 프로젝트 문서에 이미 "이 액션은 구현하는 쪽이 직접 실행해도 된다"고 사전 승인이 적혀 있었는데도, 그 세션 자체의 위험도 분류기는 그 문서를 몰랐다 — main 병합처럼 되돌리기 어려운 액션은, 사전 승인 여부와 무관하게 실행하는 그 순간에 다시 한번 사람의 확인을 요구하도록 설계돼 있었던 것이다.

두 가지 선택지가 있었다 — 그 세션의 권한 설정을 바꿔서 이 종류의 액션을 앞으로도 계속 허용하거나, 아니면 이번 한 번만 직접 GitHub에서 눌러주는 것. 후자를 골랐다. 안전장치를 넓히는 것보다, 필요한 순간에만 직접 손을 대는 쪽이 더 나은 선택이라고 판단했다.

## CodeRabbit이 진짜 버그를 하나 찾아내다

Draft를 풀자 그동안 조용했던 게 하나 움직였다 — CodeRabbit이라는 AI 코드 리뷰 봇이다. Draft 상태였던 동안은 "Review skipped: draft pull request"로 계속 건너뛰고 있었는데, Ready로 바뀌자마자 실제로 리뷰를 남겼다.

리뷰를 GitHub 화면으로 하나씩 보는 대신, GitHub API로 통째로 가져와서 한 번에 훑었다. 13개의 실행 가능한 코멘트가 있었다. 대부분은 테스트 커버리지를 좀 더 촘촘히 하라거나, 문서 표현을 더 정확히 하라는 수준의 nitpick이었다. 그런데 그중 하나가 진짜였다.

`product_content_controller`와 함께 새로 만든 통합 뷰(`product_content/show.html.erb`)의 "학습 상태"(완료 표시) 패널 조건이 `user_signed_in?` 하나만 남아 있었다 — 마이그레이션 전 Claudox 전용 화면에 있던 "부록 챕터는 진도 추적에서 제외한다"는 조건이 통합 과정에서 조용히 빠져 있었던 것이다. 라이선스를 산 유저가 부록(90/91)을 보면, 없어져야 했던 "완료 표시" 버튼이 다시 나타나는 실제 회귀였다.

CodeRabbit의 코멘트를 하나하나 코드로 직접 대조해봤다. 다른 하나(체크아웃 흐름의 `.fetch(:product_code)` 관련 지적)는 실제로는 도달할 수 없는 코드 경로라는 게 확인돼 기각했고, `/rewind` 명령이 "존재하지 않는다"는 지적도 확인해보니 CodeRabbit이 틀린 것이었다(실제로 존재하는 공식 기능이었다). 반대로 나머지 대여섯 개는 회귀는 아니지만 반영해두면 좋을 개선이었다 — 다만 이번엔 딱 하나(부록 회귀)만 고치고, 나머지는 대기 큐에 등록해뒀다. 자동화된 리뷰라고 전부 믿거나 전부 무시하는 대신, 하나하나 실제 코드로 검증한 뒤 무엇을 지금 처리하고 무엇을 미룰지 정하는 것 — 그게 이번에 새로 배운 것이었다.

## 병합, 그리고 배포 중 터진 진짜 장애

CodeRabbit 대응까지 끝나자 병합을 진행하기로 했다. 이번에도 `gh pr merge` 자체는 세션의 위험도 분류기가 막았고, 그래서 이번엔 내가 직접 GitHub에서 눌렀다 — 병합 방식은 스쿼시 머지. 5단계에 걸쳐 쌓인 개별 커밋 이력 대신 하나의 커밋(`d11e168`)으로 합쳐졌지만, 커밋 메시지 안에 6개 라운드의 메시지가 전부 이어붙어 있어서 각 단계의 의도와 발견은 여전히 `git log`로 확인할 수 있었다.

병합되자 Railway가 자동으로 새 배포를 시작했다. 그런데 배포가 끝난 직후, 마이그레이션이 아직 안 돌아간 상태에서 새 코드가 먼저 떠 있는 순간이 있었다 — `/pricing`에 새로 추가된 `tagline`/`landing_page_path` 컬럼을 코드가 참조하는데, 프로덕션 DB엔 아직 그 컬럼이 없었다. 실제로 `curl`로 확인해보니 500이 떨어지고 있었다. "당연히 되겠지"라고 넘기지 않고 직접 확인했기 때문에 바로 잡아낼 수 있었던 장애였다.

`railway run bin/rails db:migrate`로 마이그레이션을 돌리려 했는데 이번엔 이게 실패했다 — `railway run`은 로컬 프로세스에 환경변수만 심어주는 방식이라, Railway 내부 전용 DNS(`postgres.railway.internal`)를 내 로컬 환경이 해석하지 못했다. 대신 `railway ssh`로 실제 배포된 컨테이너 안에 들어가서 그 안에서 마이그레이션을 실행하니 바로 해결됐다. `/pricing`도 즉시 200으로 돌아왔다.

`aistart` 상품 데이터도 마찬가지로 "자동으로 반영됐을 것"이라 가정하지 않고 직접 확인했다 — 역시나 아직 `chatdox`·`claudox` 둘뿐이었다. `railway ssh`로 시딩 코드를 한 번 더 직접 실행해서 등록을 마쳤다. 이후 비로그인 상태로 `/content/aistart/01`이 실제 콘텐츠를 렌더링하는 것, `/pricing`에 카드가 3개로 늘어난 것, 기존 Chatdox·Claudox의 게스트 접근 한도와 마케팅 페이지까지 전부 curl로 하나하나 확인했다. 전부 회귀 없이 정상이었다.

## 여기까지다

6단계(원래 20장을 쪼개자던 A안 재검토)는 여전히 보류 중이지만, 그건 애초에 별도의 콘텐츠·사업 결정으로 남겨둔 것이었다. 이 병합으로 다상품 플랫폼 일반화 프로젝트 자체는 실제로 끝났다 — 코드는 상품이 몇 개든 늘어날 수 있는 구조가 됐고, 그 사실을 세 번째 실제 상품(`aistart`)으로 프로덕션에서까지 증명했다.
