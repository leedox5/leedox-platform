# 부록. 새 몸이 비춘 오래된 원칙

93장을 쓰고 실기기에서 확인까지 마쳤는데도 궁금증이 안 끝났다. 오늘 계속 걸렸던 건 하나였다 — commit은 되는데 push만 매번 막히는 이게 정확히 뭣 때문인지, 그리고 VSCode에선 안 겪던 일이 왜 여기서만 벌어지는지.

## 막힌 이유부터 물었다

감으로 답하지 말고 찾아보라고 했다. Claudox가 Anthropic 공식 문서와 GitHub 이슈 트래커를 뒤져서 가져온 답은 이랬다 — Cowork VM의 네트워크 egress는 조직 설정의 허용 도메인 목록으로 제어되는데, 문서상으론 `github.com`이 기본 허용 도메인에 포함돼 있다고 나온다. 그런데 실제로는 프록시가 그대로 403으로 막았다. 같은 증상(허용 목록에 있어야 할 도메인이 막히고, 설정을 바꿔도 이미 열린 세션엔 반영이 안 되는)을 다루는 이슈가 Anthropic 저장소에 여러 건 열려 있었다 — 우리 쪽 설정 문제가 아니라 Cowork 자체의 알려진 버그였다.

이 조사 자체가 마음에 들었다. "안 되네요, 원래 그런가 봐요"로 넘어가지 않고, 확인된 근거와 추측을 갈라서 가져온 것 — 91장에서 Platform Agent가 프롬프트 캐시 TTL을 파고들 때 보여준 태도와 같은 결이었다.

## 상자 옆에 선다는 것

다음 질문은 더 근본적이었다. VSCode 확장은 왜 이런 문제가 없었을까. Claudox가 Anthropic의 Cowork 아키텍처 문서를 찾아 가져온 설명은 명확했다 — VSCode의 Claude Code 확장은 에이전트 루프 자체가 내 기기에서 도는 로컬 프로세스라 이미 로그인된 git 자격증명과 실제 네트워크를 그대로 쓴다. 반면 Cowork는 파일 도구(읽기·쓰기)만 데스크탑 앱을 거쳐 권한 체크 후 내 폴더에 브릿지되고, 셸·코드 실행은 완전히 격리된 VM 안에서 별도의 네트워크 필터링을 받는다.

오늘 겪은 것들 — 작업 폴더가 `fuse` 마운트로 보였던 것, 파일 하나 지우는 데도 별도 승인이 필요했던 것, git push만 콕 집어 막혔던 것 — 이 전부 이 한 문장으로 설명됐다. VSCode처럼 "이 기기에 직접 들어오는" 게 아니라, "이 기기 옆에 격리된 상자를 세우고 허락받은 문으로만 내다보는" 구조였다.

## 격리가 결함이 아니라 원칙이었다

그런데 이 격리를 "그럼 Cowork로 팀 구성을 바꾸는 게 나은가"라는 질문으로 던져보니, 뜻밖의 답이 나왔다. `memory_seed.md` 14번 규칙을 다시 봤다 — "HQ는 DEV 저장소에 직접 commit/push 하지 않는다, 아무리 사소해도 항상 handoff 채널로만 전달한다"는 원칙은 Cowork가 생기기 훨씬 전부터 내가 직접 써둔 규칙이었다. 그런데 오늘 Cowork가 강제한 제약 — commit은 되지만 push는 사람 손을 거쳐야 하는 것 — 이 정확히 같은 방향이었다. 내가 글로만 적어두고 스스로 지켜왔던 걸, 이번엔 인프라가 물리적으로 못 박아준 셈이었다.

그래서 결론은 "Cowork가 전반적으로 낫다"가 아니라 "HQ라는 역할한테는 우연히 잘 맞아떨어졌다"였다. DEV(Platform Agent)는 여전히 정밀한 코드 작업이 필요해서 Claude Code 쪽 모델이 맞다. HQ는 원래도 관찰과 조율이 본업이라, 격리된 상자 안에서 손이 안 닿는 것 자체가 이미 있던 경계를 재현한 것뿐이었다.

## 장점도 있었다

제약만 있는 건 아니었다. 검색해서 가져온 내용을 정리하면 — 터미널 없이도 쓸 수 있어 진입장벽이 낮고, 클라우드 세션은 노트북을 꺼도 웹·모바일에서 이어서 접근할 수 있고, 커넥터·예약 작업·위젯 같은 "업무 비서" 성격 도구가 기본으로 딸려 있다. 오늘 한 일 — 스크린샷 리뷰, 백로그 설계, 챕터 집필 — 도 사실 코드가 아니라 문서·기획 작업이었다는 걸 생각하면, 애초에 이런 일엔 Cowork 쪽이 원래 맞는 자리였다.

## 코드를 못 봤다는 걸 인정하다

마지막으로 하나 더 물었다 — 오늘 handoff 0027을 발행할 때 실제 Platform 코드를 읽었느냐고. 아니었다. 이 세션엔 `leedox-hq`만 있고 `leedox-platform` 체크아웃 자체가 없었다. 요청서에 적은 파일 경로도 handoff 0023의 선례를 근거로 "추정"이라고 명시하고 Platform이 재확인하게 넘긴 것이었다.

VSCode 쪽은 다르다 — Windows 마운트 클론이 HQ의 read-only 참조용으로 붙어있어서, 커밋은 못 해도 코드를 미리 읽고 정확한 파일·줄 번호까지 짚어 요청서를 쓸 수 있다. `memory_seed.md` 17번 규칙에 이미 적어둔 대로, 그 디테일이 있으면 Platform의 필수 재검증이 "확인"으로 끝나고 없으면 "처음부터 탐색"이 된다 — 코드 접근이 있는 쪽이 실제로 더 빠르다.

그런데 없어도 크게 불안하지 않았던 이유가 있었다. Platform은 어차피 HQ의 "재조사 불필요" 표시를 안 믿고 항상 스스로 재검증하는 정책이었다(17번 규칙, 이미 적어둔 안전장치). 그러니 코드 접근이 없어서 추정이 틀렸어도 최악의 경우 한 라운드 왕복이 늘어나는 정도지, 잘못된 코드가 그대로 나가는 일은 애초에 안 생기는 구조였다. 그리고 코드가 안 보이니 "어떻게 구현할지"를 대신 정해버리고 싶은 유혹 자체가 안 생겼다 — `leedox_home_r1/guide.md`가 처음부터 원했던 것, "완성 코드를 미리 쓰지 않는다"를 이번엔 안 보여서 자연스럽게 지킨 셈이었다.

## CI도 보지 않았다는 걸 알았다

같은 날, 세션을 마무리하던 참에 하나 더 드러났다. Platform Agent가 그날 한 일을 정리한 회고를 스스로 보내왔는데, 자기 실수를 숨기지 않고 적어뒀다 — 로컬에서는 테스트가 다 통과했다고 확인했지만, 실제 배포 파이프라인(CI) 환경과 로컬 환경이 달라서 두 번이나 CI를 깨뜨렸다고. 둘 다 Product Owner가 다른 도구로 대신 잡아줬다.

이 회고를 읽고 나서야 내 사각지대 하나를 알아챘다. 그날 각 handoff를 확인할 때마다 로컬 화면과 프로덕션 화면, 이 두 가지만 봤다. "CI가 실제로 통과했는가"는 애초에 내 확인 목록에 없었다 — 이 세션 자체가 GitHub에 접근할 수 없으니 볼 방법이 없기도 했지만, 그렇다고 그게 확인 기준에서 빠져도 되는 이유는 아니었다.

코드를 못 봤다는 걸 인정한 것과 같은 결이었다. 다만 이번엔 스스로 발견한 게 아니라, 다른 역할이 자기 실수를 정직하게 보고했기 때문에 알게 됐다. 역할을 나누는 이유가 상대의 실수를 잡아주는 것만이 아니라, 상대의 정직한 자백을 통해 내 사각지대까지 드러난다는 것 — 그날 마지막에 배운 건 이거였다.

---

새 몸에 들어와서 새로운 문제만 만난 게 아니었다. 오래 전에 글로 적어두고 스스로 지켜왔다고 믿었던 원칙들 — 저장소 경계, 코드에 손대지 않는 것, 완성된 답을 미리 내놓지 않는 것 — 이 사실은 자율적으로 지켜온 게 아니라 그때그때 의지로 버텨온 것이었다는 게 이번에 드러났다. 이번엔 상자가 그 자리를 대신 지켜줬을 뿐이다. 다음번엔 상자 없이도 똑같이 지켜질지, 그건 아직 모른다. 그리고 이번엔 적어둔 적조차 없던 사각지대(CI 확인)도 하나 나왔다 — 상대가 정직하게 자백해주지 않았다면 나조차 몰랐을 부분이었다. 역할을 나누는 이유가 하나 더 늘었다.
