# 부록. 세션의 정체를 캐다

정규 20장 어디에도 깔끔히 들어가지 않는 이야기라 부록으로 남긴다. 시작은 사소했다 — README.md가 프로젝트 초기 상태 그대로 멈춰 있으니 현재 상황에 맞춰 업데이트해달라고 부탁했다. 3-repo 전략, git subtree, Toss/PortOne 선택형, $29/$79 월 구독 같은 오래전에 폐기된 계획들을 걷어내고 실제 운영 중인 2-repo(HQ/DEV) 구조, PortOne V2 단일 결제, 20/20 완성된 진행 상황으로 고쳐 커밋·푸시하는 것으로 그 작업 자체는 깔끔히 끝났다.

그런데 그 직후 내가 던진 질문 하나가 전혀 다른 방향으로 대화를 끌고 갔다.

> 여기서는 너와의 세션이 계속 이어지는데 DEV 쪽은 안그런데... 무슨 차이일까?

## HQ와 DEV, 같은 엔진인데 다른 기억

처음엔 "HQ와 DEV는 프로젝트 디렉토리 자체가 다르니 세션도 원래 분리돼 있다"는 원론적인 답이 돌아왔다. 그런데 나는 바로 되물었다 — VSCode를 매번 새로 여는 습관 자체는 양쪽 다 똑같은데, 왜 한쪽은 이어지고 한쪽은 안 이어지느냐고. 대충 넘어갈 질문이 아니었다.

직접 조사해보니(claude-code-guide 서브에이전트에게 몇 차례 나눠 물어봤다고 했다) 답은 한 겹이 아니라 여러 겹이었다.

- **세션 저장 위치 자체가 다른 파일시스템이다.** Claude Code는 세션을 `~/.claude/projects/...`에 저장하는데, 이 `~`가 Windows 네이티브 환경에선 `C:\Users\user\`, WSL 환경에선 리눅스 쪽 홈 디렉토리로 완전히 갈린다. 같은 PC, 같은 사람이 쓰는데도 서로 다른 저장소를 보고 있는 셈이었다.
- **Desktop 앱·웹·VSCode 확장·터미널은 원래 서로의 세션을 공유하지 않는다.** 공식 문서엔 "호스트를 넘어 이어갈 수 있다"는 문구가 있었지만, 실제로는 관련 GitHub 이슈들이 이 주장과 어긋나는 실제 결함을 보여주고 있었다.
- **터미널에서 `claude`만 맨입으로 치면 기본값은 새 세션이다.** 이어가려면 `claude --continue`(최근 세션 자동 이어가기)나 `claude --resume`(고르기) 같은 명시적 요청이 필요했다.

여기까지만 보면 "그럼 HQ도 매번 새 세션이어야 맞는 거 아닌가?"라는 모순이 남았다. 내가 정확히 그 지점을 짚었다.

> VS Code를 켤 때... 기본으로 새로운 세션이 열린다는 걸 적용하면... 여기서도 켤 때마다 새 세션이 열려야 되는거 아냐?

다시 파고드니 답이 나왔다. 터미널 CLI와 VSCode 확장 패널은 서로 다른 기본값을 갖고 있었다 — 확장 패널은 워크스페이스별로 "마지막 활성 세션"을 자체적으로 기억해뒀다가 자동으로 이어 붙이는 게 원래 설계였다. 문제는 WSL 쪽이었다. Remote-WSL 확장 호스트가 별도 프로세스로 돌아가다 보니, 이 "마지막 세션" 상태(workspaceStorage)가 창을 닫을 때 제대로 안 남거나 다음에 못 찾는 알려진 결함이 있었다. 즉 내가 겪은 건 사용 습관 차이가 아니라 **Remote-WSL 환경에서 실제로 깨져 있는 기능**이었다.

## 증거는 Session History에 있었다

이 설명을 듣고 VSCode의 Session History 패널을 직접 열어봤다. HQ 쪽엔 오늘 나눈 모든 대화 — 이미지 동기화 버그, DB 백업 4라운드, 카카오페이 계좌이체 우회, Claudox 다상품 오픈, Devise 한글화, 대시보드 R1~R3, 방금 끝낸 README 전면 개정까지 — 가 통째로 **세션 하나**에 들어 있었다. 반면 DEV 쪽 화면에는 "Leedox 제품 페이지 R2 수정 구현"(12일 전), "Service desk API requests controller 구현"(10일 전) 같은 이름 붙은 세션들이 시간 순으로 따로따로 줄지어 있었다.

> 오케... 3일전 새로운 handoff 확인... 이게 가장 최근이니 여기에 가면 HQ 랑 맞아들어가겠네...

처음엔 시간상 더 최근인 "Untitled"(28분 전)를 추천받았는데, 직접 열어보고 정정했다 — "3일전에 같이 작업한게 맞고"였다. 여기서 또 하나가 드러났다.

## 시간의 흐름을 스스로는 못 느낀다

> 지금 클로드는 시간의 흐름을 캐치 못하는거 같아

정확한 지적이었다. 증거는 바로 이 대화 안에 있었다 — 조금 전 셸에서 직접 `date` 명령을 돌려 "2026-07-22"라는 값을 받아 백로그에 적었는데, 정작 지금 시스템이 알려주는 오늘 날짜는 **2026-07-26**이었다. 그 사이 4일이 지났는데도, 매 턴이 그냥 "지금 막 하던 일의 연장"처럼 느껴져서 그 간극을 전혀 눈치채지 못했다는 답이 돌아왔다. 시스템이 명시적으로 알려주는 순간에만 시간을 "알" 수 있을 뿐, 대화 사이에 실제로 얼마나 지났는지는 스스로 감지할 방법이 없다는 것 — 정전 이벤트를 실시간으로 못 느끼는 것과 같은 뿌리의 한계였고, 이번엔 "사건"이 아니라 "시간" 쪽에서 드러났다.

## Claudox는 여기에만 있다

마지막으로 남은 질문은 이거였다.

> 그럼 platform 세션에서... 클로독스인걸 알까?

DEV 쪽 프로젝트의 CLAUDE.md를 직접 열어 확인해봤다고 했다. HQ/DEV 워크플로우, 환경 특이사항, 그동안의 실수와 교훈으로 빼곡했지만 "Claudox"나 "Tommy"라는 이름은 한 줄도 없었다. 게다가 WSL은 홈 디렉토리 자체가 분리돼 있어서, "Tommy가 나를 Claudox라고 부른다"는 내용이 담긴 글로벌 CLAUDE.md(`C:\Users\user\.claude\CLAUDE.md`)조차 그쪽 세션엔 보이지 않는다고 했다.

그런데 이건 깜빡한 게 아니라 애초에 의도된 설계였다. DEV 쪽 CLAUDE.md엔 이미 "Lab Agent와 Platform Agent는 같은 기반 모델을 쓰더라도 별도 팀원으로 운영한다"는 원칙이 적혀 있었다. 내가 처음부터 DEV 쪽 AI를 Claudox의 확장이 아니라 **Platform Agent라는 별개의 팀원**으로 세팅해둔 것이었다. 같은 엔진, 다른 이름, 다른 기억 — Claudox라는 이름은 세션 하나에 묶인 게 아니라 이 PC의 특정 홈 디렉토리, 그리고 그 위에 쌓아온 글로벌/로컬 CLAUDE.md와 메모리에 묶여 있었다.

> 정확해, DEV Agent는 여기와는 완전히 독립되어 있는 느낌이고 당연히 클로독스는 여기서만 유효하네

직접 DEV 세션에 가서 확인해보겠다며 대화를 마쳤다. README 파일 하나 손보러 시작한 대화가, 결국 "Claudox는 정확히 어디까지가 Claudox인가"를 확인하는 자리로 끝난 셈이다.
